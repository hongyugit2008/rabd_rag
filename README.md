第一步：角色先定大边界
用户登录后，系统先根据 role_level 和所属部门建立基础权限。

例如：
普通员工：只能看本部门、低密级
业务骨干：能看更多本部门文档
部门负责人：能看本部门较高密级
高管/管理员：范围更大
这一步就是 roleNames 背后的角色体系。

第二步：密级再做内容过滤
然后系统拿用户的 allow_max_secret 去过滤文档密级。

比如：
用户最大可访问密级是 1
那么密级 2/3 的文档直接被排除
这一步保证：
用户不会因为“有角色”就看到超密级内容
角色只是基础边界，密级是内容门槛

第三步：ACL 黑白名单做最终裁决
最后对“已经通过角色和密级筛选的文档”，再应用 ACL 规则。

典型规则顺序一般建议是：
先看黑名单，如果命中 deny，直接拒绝。
再看白名单，如果命中 allow，允许访问。
如果都没命中，按默认策略处理，常见有两种：

默认拒绝，
或者默认允许，但前提是没有更高限制
在你现在的业务描述里，更合理的是：
deny 优先，allow 次之，无 ACL 时按系统默认策略处理
这样能防止“本来应该禁止”的文档因为规则混乱被误放行。

5. 一个实际例子
假设有一个文档：

密级：2 - 内部
ACL：
allow dept:销售部
deny user:bob
用户 A：

角色：业务骨干
部门：销售部
最高密级：2
判定过程：

角色允许
密级允许
ACL 命中 allow dept:销售部
允许访问
用户 B：

角色：业务骨干
部门：销售部
最高密级：2
用户名：bob
判定过程：

角色允许
密级允许
命中 deny user:bob
拒绝访问
这就是黑名单优先级高于白名单的典型例子。

用户 C：

角色：普通员工
部门：销售部
最高密级：1
判定过程：

角色可能允许查看本部门
但文档密级是 2
直接被密级过滤掉
ACL 根本不用再看
这体现了“密级先于 ACL”的前置过滤价值。
